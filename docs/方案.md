# 《方案》第一部分

> 面向资源受限嵌入式平台的可移植 C++ 2D FLIP/PIC 流体模拟核心
> 文档日期：2026-09-17

## 1. 项目定位

### 1.1 项目的最终形态

本项目最终应成为一个面向低算力、低内存、低成本嵌入式平台的可移植 C++ 2D FLIP/PIC 流体模拟库。

项目主体是流体模拟核心，而不是 ESP32 固件、LED 灯效框架或 MPU6050 应用。当前 ESP32-S3、16×16 WS2812 灯板和 MPU6050 组成的水流灯，是该流体核心的第一个参考应用，用于验证算法在真实资源受限硬件上的运行能力。

同一套核心源码应能够比较容易地运行于：

- ESP32 系列 MCU；
- STM32；
- 其他 Cortex-M MCU；
- 国产 MCU；
- Linux、Windows 等 PC 仿真环境；
- 后续可能使用的 LCD、普通显示器或其他输出设备。

平台迁移不应要求修改 FLIP/PIC 求解流程。平台差异应被限制在流体核心之外。

### 1.2 核心职责

流体核心负责：

- 保存粒子位置和速度；
- 保存网格速度、压力、密度及单元类型；
- 对粒子进行重力积分和位置推进；
- 处理粒子之间的互斥；
- 处理粒子与模拟边界的碰撞；
- 将粒子速度传递到网格；
- 计算粒子密度；
- 求解不可压缩压力；
- 使用 PIC/FLIP 混合将网格速度传回粒子；
- 向调用方提供粒子和网格模拟结果。

流体核心不负责：

- LED 刷新、RGB 颜色和调色板；
- gamma、亮度和具体显示设备的数值映射；
- MPU6050 或其他 IMU 的读取；
- GPIO、I2C、SPI、RMT 等外设操作；
- FreeRTOS task、锁、延时或任务调度；
- 获取系统时间；
- 日志输出；
- ESP-IDF 或其他厂商 SDK 的初始化和错误类型；
- 应用模式、按键和用户交互。

### 1.3 分层关系

项目的依赖方向应为：

```text
具体应用
  └─ LED / LCD / PC 窗口等显示与交互
       └─ ESP32 / STM32 / Linux 等平台适配层
            └─ 平台无关的流体模拟核心
```

上层可以依赖下层，下层不能反向依赖上层。流体核心不能包含任何特定平台头文件，也不能通过条件编译把不同 MCU SDK 塞入核心实现。

### 1.4 资源受限原则

核心必须以没有 PSRAM、没有操作系统、RAM 较小且 CPU 性能有限的设备为设计基准。

核心需要满足：

- 网格宽度和高度可配置；
- 最大粒子数可配置；
- pressure iteration 次数可配置；
- particle push iteration 次数可配置；
- FLIP/PIC 混合比例可配置；
- 时间步长由调用方提供；
- 初始化前可以计算所需内存；
- 初始化后不得在 `step()` 中分配内存；
- 不默认存在 heap、PSRAM、RTOS 或 FPU；
- 不要求异常、RTTI、线程或虚函数；
- 可以通过降低网格、粒子和迭代次数适配更便宜的 MCU。

### 1.5 第一阶段非目标

第一阶段不处理：

- fixed-point 实现；
- SIMD、汇编或特定 MCU 指令优化；
- STM32 或其他 MCU 的完整工程；
- benchmark 系统；
- 3D 流体模拟；
- GPU 加速；
- C 和 C++ 两套独立算法实现；
- 对现有数值算法的大规模重写或调参。

第一阶段首先保证算法边界清晰、核心可独立编译，并保持现有 ESP32 水流效果的行为。

## 2. 实现策略

### 2.1 单一 C++ 实现

流体核心只维护一套 C++ 实现，不同时维护相同算法的 C 和 C++ 版本。

维护两套实现会导致：

- Bug 修复无法保证同步；
- 参数和默认行为逐渐不一致；
- 不同版本的数值结果发生分叉；
- 测试和优化工作重复；
- 平台移植者无法判断哪一份是权威实现。

如果未来有严格的纯 C 工程需要使用该库，可以在 C++ 核心外增加轻量 C binding。C binding 只负责数据类型和函数调用转换，不复制 FLIP/PIC 算法。

### 2.2 C++ 语言基线

核心最低语言标准确定为 C++11，并允许使用 C++14 编译器进行构建，但不能依赖 C++17 及以上特性。

选择 C++11 的原因：

- 兼容更多旧版本 ARM GCC 工具链；
- 降低国产 MCU 和厂商工具链的接入门槛；
- 当前 FLIP/PIC 算法不需要 C++17 特性；
- ESP-IDF、主流 Cortex-M 工具链和 PC 编译器均能支持；
- 避免移植方仅为使用该库而升级整个工程工具链。

核心可以使用：

- 类和封装；
- `enum class`；
- C++11 支持范围内的 `constexpr`；
- 简单模板；
- 移动语义；
- 自定义的数组、网格和粒子只读视图。

核心不依赖：

- `std::span`；
- 结构化绑定；
- `if constexpr`；
- filesystem；
- iostream；
- 标准线程库；
- 异常和 RTTI；
- 会在运行时自动扩容的标准容器。

### 2.3 内存管理策略

流体核心不应自行假设内存来源。核心使用由调用方提供的连续 workspace，并负责在初始化时将这块内存划分为粒子、网格和临时工作数组。

调用方可以根据平台决定 workspace 位于：

- 静态全局数组；
- 普通 heap；
- ESP32 internal RAM；
- PSRAM；
- STM32 的特定 SRAM 区域；
- linker script 指定的 section；
- PC 环境中的动态数组。

核心应提供内存需求查询能力：

```cpp
std::size_t requiredMemory(const FluidConfig& config);
```

典型初始化流程为：

```text
1. 应用构造配置；
2. 查询所需内存；
3. 应用准备 workspace；
4. solver 使用该 workspace 初始化；
5. 后续 step 重复使用已有内存。
```

实时循环中不得调用 `malloc`、`calloc`、`realloc`、`free`、`new` 或 `delete`。

### 2.4 数值行为保持原则

第一次迁移应保持当前算法行为，包括：

- 粒子的初始排列方式；
- 重力积分顺序；
- 粒子空间邻域划分方式；
- 粒子互斥处理顺序；
- 碰撞和边界限制方式；
- 粒子到网格的插值方式；
- 压力求解顺序；
- PIC/FLIP 混合公式；
- 当前默认物理参数；
- 当前 16×16 ESP32 示例的可见效果。

第一阶段只改变模块归属、接口和依赖，不同时改变求解器数学行为。算法优化必须在核心迁移完成且存在回归测试以后单独进行。

### 2.5 平台优化策略

标准 C++ 标量实现是权威实现和行为基准。

`esp-dsp`、CMSIS-DSP 或其他平台加速不能成为核心的必需依赖。后续如需优化，应作为可选后端，并满足：

- 不改变公共接口；
- 不改变数据语义；
- 标量实现始终可以独立使用；
- 优化实现必须通过与标量实现的结果对比测试。

### 2.6 ESP32 参考应用

ESP32 工程保留为 reference example，负责：

- 初始化 ESP-IDF；
- 创建和调度 FreeRTOS task；
- 获取帧时间或固定 `dt`；
- 读取 MPU6050；
- 将 IMU 数据转换为二维重力；
- 为核心提供适合 ESP32 的 workspace；
- 将粒子或密度结果转换为 LED 亮度和颜色；
- 处理灯板走线、按键和模式切换。

ESP32 example 可以选择 internal RAM 或 PSRAM，但该选择不得进入流体核心。

### 2.7 DOOM Fire 的位置

DOOM Fire 不是 FLIP/PIC 流体核心的一部分，应作为独立效果模块存在。

```text
fluid2d    FLIP/PIC 流体模拟库
doom_fire  DOOM 风格火焰效果库
```

DOOM Fire 可以采用相同的平台解耦原则，也可以与流体 example 共享 LED、IMU 和任务适配代码，但不能进入流体核心的状态、接口或构建依赖。

## 3. 核心接口

### 3.1 调用模型

核心的目标使用方式接近：

```cpp
FluidSolver solver;

FluidStatus status = solver.initialize(config, workspace, workspace_size);
solver.setGravity(gx, gy);
solver.step(dt);

ParticleView particles = solver.particles();
GridView density = solver.densityGrid();
```

调用方负责提供时间步长。核心不能读取系统 timer，也不能自行延时或创建线程。

### 3.2 配置内容

`FluidConfig` 应按职责表达配置，而不是暴露所有内部局部变量。

#### 容量配置

- 网格宽度；
- 网格高度；
- 最大粒子数；
- 邻域搜索所需容量；
- workspace 大小。

容量配置直接决定 RAM 使用量，初始化后通常不能在不重新初始化的情况下改变。

#### 求解质量配置

- pressure iterations；
- particle push iterations；
- FLIP/PIC ratio。

这些参数主要影响 CPU 使用量和模拟质量，可以允许在容量不变的情况下调整。

#### 物理配置

- 流体密度；
- 粒子半径或半径系数；
- 初始填充比例；
- 初始填充宽度；
- 重力缩放；
- 压力 over-relaxation；
- 密度漂移补偿选项。

第一阶段应优先保留现有默认值，只开放迁移和资源控制真正需要的参数，避免在架构迁移时扩大调参范围。

### 3.3 运行时输入

每帧运行时输入只包括：

- 二维重力 `gx`、`gy`；
- 时间步长 `dt`。

输入的来源由平台层决定。例如：

- ESP32 example 从 MPU6050 得到重力；
- PC example 可以由鼠标或键盘产生重力；
- 无传感器 MCU 可以使用固定重力；
- 测试程序可以使用预设输入序列。

### 3.4 粒子输出

核心应提供非拥有型、只读的粒子视图。视图至少包含：

- 当前粒子数量；
- 粒子位置数据；
- 可选的粒子速度数据；
- 每个粒子的分量数量；
- 明确的数据排列方式。

调用方不得通过只读视图改变 solver 内部状态。视图不拥有内存，其生命周期不得超过 solver 和 workspace。

### 3.5 网格输出

核心应提供非拥有型、只读的网格视图。视图至少包含：

- 网格宽度；
- 网格高度；
- stride；
- 数据指针；
- 数据含义和有效范围。

网格输出应表达模拟数据，例如原始密度或相对静止密度，而不是 LED 亮度。

以下内容必须由应用层完成：

- density clamp；
- gamma；
- 热力图或调色板；
- RGB 转换；
- LED 通道亮度限制；
- 蛇形灯板坐标映射。

### 3.6 错误处理

核心不依赖异常。初始化和需要验证的操作返回明确状态，例如：

```cpp
enum class FluidStatus {
    Ok,
    InvalidConfig,
    InsufficientMemory,
    CapacityExceeded
};
```

配置错误、容量不足和 workspace 不足应在初始化阶段发现，不能等到实时循环中才失败。

### 3.7 生命周期和所有权

接口必须明确以下约束：

- `requiredMemory()` 可以在 solver 初始化前调用；
- solver 不拥有调用方提供的 workspace；
- workspace 在 solver 生命周期内必须持续有效；
- 初始化完成后 `step()` 不申请或释放内存；
- `ParticleView` 和 `GridView` 引用 solver 内部数据；
- solver 重置或销毁后，旧 view 失效；
- 改变网格或最大粒子数需要重新初始化；
- 改变迭代次数和 FLIP/PIC ratio 不应要求重新分配内存。

### 3.8 第一阶段最小接口范围

第一阶段的核心接口只需要覆盖：

1. 验证配置；
2. 计算所需内存；
3. 使用外部 workspace 初始化；
4. 设置二维重力；
5. 推进一步模拟；
6. 读取粒子视图；
7. 读取密度网格视图；
8. 将模拟重置到初始状态。

第一阶段暂不加入：

- 运行时改变网格容量；
- 动态增加或删除粒子；
- 多种流体材料；
- 任意形状障碍物编辑；
- 状态序列化；
- 回放系统；
- 插件式求解器；
- 多线程接口。

这些能力只有在出现明确使用需求，并且不会破坏嵌入式资源预算时才考虑增加。
